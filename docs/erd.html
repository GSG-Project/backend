Relationship guide

Each badge on the diagram matches a card below. Cardinality is read from parent to child.

R1

Experiment to ExperimentModel

1 : 2 (MVP)

An experiment is the comparison request itself: one prompt and the models chosen for it. In the MVP it lists exactly two models, each stored as one ExperimentModel row. The backend enforces the limit of two.

experiment_model.experiment_id
R2

AIModel to ExperimentModel

1 : 0..N

A model (one with is_judge false) can take part in many experiments, and an experiment uses two models. ExperimentModel resolves this many-to-many link. Unique (experiment_id, ai_model_id) stops the same model being picked twice in one experiment.

experiment_model.ai_model_id
R3

Experiment to Run

1 : 1..N

A run is one execution of an experiment. Keeping it separate lets the same experiment be executed again later while every earlier result is preserved. The MVP creates one run per experiment.

run.experiment_id
R4

Run to ModelResponse

1 : 1..N

Each run stores one response per selected model, so two in the MVP. A failed API call still gets a row, with status and error_message filled in and the measured fields left NULL. A success row must have response_text.

model_response.run_id
R5

ExperimentModel to ModelResponse

1 : 0..N

This ties each response to the model that produced it within that experiment. Across several runs the same ExperimentModel gets one response per run, which Unique (run_id, experiment_model_id) guarantees.

model_response.experiment_model_id
R6

ModelResponse to Evaluation

1 : 0..N

The AI Judge scores a response once per criterion (score 1 to 10), so a successful response has up to four Evaluation rows. A failed response cannot be scored. Unique (response_id, criterion_id) prevents duplicate scores.

evaluation.response_id
R7

EvaluationCriterion to Evaluation

1 : 0..N

Criteria are shared definitions: accuracy, relevance, clarity and completeness, the criteria the judge prompt scores today. Both responses in a run are scored against the same rows, which keeps the scores comparable.

evaluation.criterion_id
+

AIModel to Run (judge)

1 : 0..N

A run records which judge model scored it. The link is optional until the run is judged and only accepts models with is_judge true. evaluation_status tells a failed judge apart from one that has not run, and a completed evaluation requires a judge. The judge's pick is stored as winner_id (an ExperimentModel of the same experiment) with judge_reasoning, both empty until the evaluation completes. No lines are drawn for these two links because they would cross the other tables.

run.judge_model_id · run.winner_id
